# 컨트랙트 보안 검증

> 기준일: 2026-09-08  
> 범위: `RevenueBridge`, `RevenueRightToken`, `MockSettlementToken` 및 Foundry 테스트

이 문서는 개발 중 수행한 보안 검증 기록이다. 전문 보안 감사 결과를 대신하지 않는다.

## 검증 현황

- 전체 테스트: 45개 통과
- 회계 invariant: 128 runs, 8,192 calls, revert 0회
- `RevenueBridge` 커버리지: 라인 90.87%, 구문 93.38%, 분기 55.00%, 함수 100%
- 검증 명령: `forge clean && forge test --summary`, `forge coverage --report summary`
- 로컬 배포: Docker Anvil 체인 ID 31337에서 실제 배포 및 역할·허용 목록·초기 잔액 조회 확인
- RPC 정상 흐름: 역할별 EOA로 투자·확정·선지급·3회 정산·종료·청구 후 부채와 잔액 검증

## 현재 보안 모델

컨트랙트가 직접 보장하는 범위는 다음과 같다.

- 등록된 상품 조건과 정산 기간을 변경하는 함수가 없음
- 허용된 투자자만 모집 기간에 투자 가능
- 실제 받은 ERC-20 금액이 계산된 금액과 다르면 전체 트랜잭션 취소
- 모집 실패 시 본인의 투자금만 환불하고 해당 수익권 소각
- 종료된 정산 기간을 순서대로 한 번만 보고 가능
- 정산 보고와 투자자 몫의 입금을 하나의 트랜잭션으로 처리
- 누적 입금액과 고정 지분으로 투자자별 청구 한도 계산
- 수익권의 투자자 간 단일·일괄 전송 차단
- 선지급·환불·정산·청구 함수의 외부 호출 재진입 방어

컨트랙트가 보장하지 못하는 범위는 다음과 같다.

- 플랫폼 수익 자료와 증빙 문서의 진실성
- 크리에이터가 같은 미래 수익을 다른 계약에 중복 양도하지 않았다는 사실
- 플랫폼 수익이 지정 정산계좌로 들어오도록 하는 법적·운영적 집행
- 정산자의 수익 보고가 실제 오프체인 수익과 일치한다는 사실
- 관리자·발행자·정산자 키의 안전한 보관

## 발견 및 처리 내역

### CRB-SEC-001 — 정산이 선지급보다 먼저 실행되면 선지급금이 잠김

- 상태: 해결
- 영향: 높음
- 원인: `withdrawAdvance`가 `Active` 상태만 허용했으며 첫 정산 후 `Settling`, 최종 종료 후 `Closed` 상태에서는 호출할 수 없었음
- 공격·오류 경로: 누구나 정산 완료 후 `closeOffering`을 먼저 호출하면 크리에이터가 모집 대금을 영구히 인출할 수 없었음
- 처리: 성공 상품인 `Active`, `Settling`, `Closed` 상태에서 미인출 선지급금 청구 허용
- 회귀 테스트: `testCreatorCanWithdrawAdvanceAfterOfferingCloses`

### CRB-SEC-002 — 수수료 차감형 결제 토큰의 회계 불일치

- 상태: 방어 확인
- 영향: 높음
- 위험: 요청 금액과 실제 수령·지급 금액이 다르면 장부상 부채와 보유 토큰 잔액이 달라질 수 있음
- 통제: 전송 전후 Bridge와 수신자 잔액 차이를 검사하고 불일치 시 revert
- 검증: 투자 입금 및 크리에이터 선지급에서 1% 수수료 토큰을 사용해 상태·토큰 이동 전체 롤백 확인
- 테스트: `testFeeOnTransferInvestmentRollsBackAccountingAndMint`, `testFeeOnTransferWithdrawalRollsBackAccountingAndPayment`

### CRB-SEC-003 — ERC-1155 수신 콜백을 통한 재진입과 발행 거부

- 상태: 방어 확인
- 영향: 높음
- 위험: 컨트랙트 투자자가 수익권 발행 콜백에서 다시 투자하거나 토큰 수신을 거부할 수 있음
- 통제: `invest`의 재진입 방어와 ERC-20 이동·ERC-1155 발행의 트랜잭션 원자성
- 검증: 콜백 재진입과 명시적 수신 거부 모두 투자 회계, 토큰 이동과 수익권 발행이 원상복구됨
- 테스트: `testReceiverCallbackCannotReenterInvestment`, `testReceiverRejectionRollsBackInvestment`

### CRB-SEC-004 — 여러 상품 사이의 회계 침범

- 상태: 불변조건 검증 추가
- 영향: 높음
- 위험: 한 상품의 선지급·정산·청구가 다른 상품의 보관 자금을 소비할 수 있음
- 통제: 전체 모집 부채와 수익 부채를 별도로 추적하고 각 상품의 누적 입금·청구 금액으로 지급 한도 계산
- 검증: 두 상품과 두 투자자의 선지급·정산·청구·종료 순서를 무작위로 조합한 8,192회 호출에서 불변조건 유지

검증하는 불변조건은 다음과 같다.

```text
Bridge 토큰 잔액
= totalEscrowLiability + totalRevenueLiability

totalClaimed <= investorRevenueTotal

성공 상품의 총 수익권 공급량과 투자자별 지분은 고정
```

## 남은 보안 검증

- ERC-20 전송 콜백에서 `refund`, `withdrawAdvance`, `settlePeriod`, `claim` 재진입 시도
- 실패 상품과 성공 상품이 동시에 존재하는 상태의 회계 invariant
- 허용 목록 제거와 일시중지 이후 기존 투자자의 환불·청구 가능 여부
- 관리자·발행자·정산자의 권한 분리와 역할 변경 경계
- 최대 정산 기간 수와 큰 금액을 사용한 가스 및 산술 경계
- Base Sepolia 배포 전 정적 분석과 독립 보안 검토

## 운영상 잔여 위험

- `SETTLER_ROLE`은 0원 수익을 포함한 기간 보고를 확정할 수 있으므로 오프체인 증빙 검증과 키 통제가 필요하다.
- 확정된 수익 보고의 수정, 음수 조정과 차지백을 지원하지 않는다.
- 정수 나눗셈 뒤 남는 최소 단위 토큰은 회수 기능 없이 Bridge에 남는다.
- 단일 Bridge가 여러 상품을 관리하므로 코드 결함과 관리자 키 위험을 모든 상품이 공유한다.
- 일반 전송으로 Bridge에 들어온 토큰은 투자자 권리를 만들지 않으며 현재 회수 경로도 없다.
