# Moa 개발 기능 명세서

## 1. 문서 목적

본 문서는 Moa MVP 구현을 위한 개발 기능 명세서다.

Moa는 5명의 참여자가 공동 자산을 관리하고, 3명 이상의 동의를 받아야 지출을 실행할 수 있는 3-of-5 멀티시그 기반 공동계좌 서비스다.

MVP의 최우선 목표는 다음 두 흐름이다.

### Happy Path

    공동계좌 생성
    → 입금
    → 지출 제안
    → 3명 승인
    → 실행 검증
    → 정상 실행

### Attack Path

    정상 지출 제안
    → 3명 승인
    → 실행 Payload 변조
    → Intent와 불일치 감지
    → 실행 차단

# 4. Account 기능

## ACCOUNT-01. Wallet 연결

사용자는 EVM Wallet을 Moa에 연결할 수 있다.

입력:

- Wallet Address
- Chain ID

출력:

- 연결된 Wallet Address
- 현재 Network
- Owner 여부

조건:

- 지원 Network가 아니면 경고한다.
- Wallet 미연결 상태에서는 Transaction 발생 기능을 제한한다.

Acceptance Criteria:

    Given Wallet이 설치되어 있을 때
    When 사용자가 연결 버튼을 선택하면
    Then Wallet 주소가 표시되어야 한다.

## ACCOUNT-02. 공동계좌 생성

5개의 Owner Wallet과 Threshold를 지정하여 새로운 Moa 계좌를 생성한다.

MVP 기준:

- Owner Count = 5
- Threshold = 3

입력:

    accountName
    owners[5]
    threshold = 3

검증:

- Owner는 정확히 5개
- 모든 Owner 주소는 유효한 EVM 주소
- 중복 Owner 불가
- threshold > 0
- threshold <= owners.length
- MVP에서는 threshold를 3으로 고정하거나 UI에서 3을 기본값으로 사용

출력:

- Account Contract Address
- Account ID
- 생성 Transaction Hash

이벤트:

    AccountCreated

## ACCOUNT-03. 공동계좌 조회

사용자가 참여하고 있는 Moa 계좌를 조회한다.

출력:

    accountAddress
    accountName
    owners
    threshold
    balance
    pendingProposalCount

Account Name 등 사용자 친화적인 정보는 Backend Metadata로 관리할 수 있다.

## ACCOUNT-04. 입금

사용자는 Moa 계좌로 자산을 입금할 수 있다. MVP에서는 Native Token을 우선 지원한다.

입력:

    accountAddress
    amount

처리:

    User Wallet
    → Multisig Account

입금에는 멀티시그 승인이 필요하지 않다.

# 5. Proposal 기능

## PROPOSAL-01. 지출 제안 생성

Owner는 공동자금 사용을 위한 Proposal을 생성할 수 있다. Proposal은 단순 Transaction 요청이 아니라 승인 대상인 Intent를 포함한다.

입력:

    purpose
    recipient
    amount
    action
    expiresAt

MVP action:

    TRANSFER

내부 생성 값:

    proposalId
    proposer
    nonce
    intentHash
    createdAt
    status
    approvalCount
    executed
    blocked

purpose는 UI 설명용 Metadata로 오프체인에 저장할 수 있다.

## PROPOSAL-02. Intent Hash 생성

승인 조건을 결정론적으로 직렬화하여 Intent Hash를 생성한다.

Hash 포함 값:

    accountAddress
    proposalId
    recipient
    amount
    action
    expiresAt
    nonce
    chainId

keccak256(abi.encode(...)) 또는 EIP-712 Typed Data를 사용한다.

동일 조건에서는 동일 Hash가 생성되어야 하며, recipient, amount, action, expiresAt, nonce, account, network 중 하나라도 변경되면 Hash가 달라져야 한다.

Acceptance Criteria:

    Intent A: recipient = HOTEL
    Intent B: recipient = ATTACKER
    Then: hash(A) != hash(B)

## PROPOSAL-03. Proposal 상태 조회

상태:

- PENDING: approvalCount < threshold
- READY: approvalCount >= threshold, not expired, not executed
- EXECUTED: 정상 실행 완료
- BLOCKED: Execution Validation 실패
- EXPIRED: 유효시간 초과

## PROPOSAL-04. Proposal 목록 조회

필터:

- 전체
- 승인 대기
- 실행 가능
- 완료
- 차단

정렬:

    createdAt DESC

# 6. Approval 기능

## APPROVAL-01. Proposal 승인

Owner가 특정 Proposal의 Intent에 동의한다.

입력:

    proposalId
    signer

또는 서명 기반:

    proposalId
    signature

조건:

- signer가 Owner여야 한다.
- Proposal이 존재해야 한다.
- 이미 실행된 Proposal이 아니어야 한다.
- 만료된 Proposal이 아니어야 한다.
- 동일 Owner의 중복 승인을 허용하지 않는다.

상태 변화:

    approvalCount += 1
    PENDING → READY  (Threshold 도달 시)

## APPROVAL-02. 중복 승인 차단

approved[proposalId][signer] == true이면 AlreadyApproved 오류를 반환한다.

## APPROVAL-03. 비Owner 승인 차단

등록된 Owner가 아닌 주소의 승인 요청은 NotOwner 오류로 차단한다.

## APPROVAL-04. 승인자 목록 조회

각 승인자는 address, approved, approvedAt 정보를 가진다.

# 7. Threshold 기능

## THRESHOLD-01. 승인 수 계산

계약은 현재 Proposal의 유효 승인 수를 계산한다.

    approvalCount
    threshold = 3

## THRESHOLD-02. 실행 가능 여부 판단

    approvalCount >= threshold

Threshold 충족은 실행의 충분조건이 아니다. 다음 Security Validation도 통과해야 한다.

    Threshold
    + Intent Match
    + Expiration

# 8. Execution 기능

## EXECUTION-01. 정상 실행

입력:

    proposalId
    executionPayload

executionPayload 최소값:

    recipient
    amount
    action

검증 순서:

1. Proposal 존재 여부
2. 이미 실행 여부
3. Threshold
4. Expiration
5. Intent / Execution Match
6. Balance
7. Execute

## EXECUTION-02. Intent / Execution 일치 검증

Proposal에 승인된 Intent와 실제 실행할 Transaction을 비교한다.

비교 항목:

- recipient
- amount
- action

필요 시 chainId, token, calldata까지 확장한다.

정상 예:

    Intent: recipient = HOTEL, amount = 320, action = TRANSFER
    Execution: recipient = HOTEL, amount = 320, action = TRANSFER
    결과: PASS

공격 예:

    Intent: recipient = HOTEL, amount = 320
    Execution: recipient = ATTACKER, amount = 320
    결과: FAIL

## EXECUTION-03. Mismatch 차단

Intent와 Execution이 다르면 Transaction을 실행하지 않는다.

- 결과: Execution blocked
- Error: IntentMismatch
- Event: ExecutionBlocked

## EXECUTION-04. 실행 완료

검증 성공 시 자산을 이동한다.

    READY → EXECUTED

Event:

    ProposalExecuted

## EXECUTION-05. 재실행 차단

한 번 실행된 Proposal은 다시 실행할 수 없다.

Error:

    AlreadyExecuted

# 9. Expiration 기능

MVP P1 기능이지만 Contract 구조에서는 처음부터 고려한다.

Proposal 생성 시 expiresAt을 설정한다.

Validation:

    block.timestamp <= expiresAt

실패 시 IntentExpired를 반환한다.

# 10. Nonce / Replay Protection

## SECURITY-01. Proposal Nonce

각 Proposal에는 고유 nonce가 있어야 한다. 같은 승인 데이터를 다른 Proposal에서 재사용할 수 없도록 한다.

## SECURITY-02. Account Binding

Intent Hash에 accountAddress를 포함한다. 계좌 A에서 승인한 Intent를 계좌 B에서 사용할 수 없어야 한다.

## SECURITY-03. Chain Binding

가능하면 chainId를 Intent에 포함하여 다른 Network에서 Approval 재사용을 방지한다.

# 11. Attack Simulation 기능

발표용 기능이며 Production 기능이 아니다.

## ATTACK-01. Attack Mode

Development / Demo 환경에서만 활성화한다.

    ATTACK_MODE=true

Production build에서는 노출하지 않는다.

## ATTACK-02. Recipient 변조

정상 Proposal의 recipient가 HOTEL일 때 Attack Mode에서 executionPayload.recipient를 ATTACKER로 바꾼다.

승인된 Proposal 자체는 수정하지 않는다. 승인된 Intent는 그대로 유지하고 실행 Payload만 변조한다.

## ATTACK-03. Attack 결과 표시

Contract 호출 결과가 IntentMismatch이면 Frontend에 다음을 표시한다.

    실행이 차단되었습니다.
    승인한 대상: HOTEL
    실제 요청: ATTACKER

# 14. Frontend 기능

## FE-01. Home

연결 Wallet, 참여중인 Moa 목록, Account Name, Balance, 참여자 수, Pending Proposal을 표시한다.

## FE-02. Account Detail

Account Name, Balance, Owners, Threshold, Recent Activity를 표시하고 입금과 지출 제안을 제공한다.

## FE-03. Proposal 생성

Form:

    purpose
    recipient
    amount
    expiresAt

Validation:

- recipient 필수
- amount > 0
- amount <= account balance
- expiresAt > current time

## FE-04. Proposal Detail

purpose, amount, recipient, expiresAt, proposal status, 승인자 목록, approvalCount / threshold를 표시한다.

Action:

- 동의하기
- 실행하기

## FE-05. Approval UX

- 미승인: 동의하기
- 승인 완료: 동의 완료
- 비Owner: 이 공동계좌의 참여자가 아닙니다.

## FE-06. Happy Result

지출 완료, 목적, 금액, 승인자 목록을 표시한다.

## FE-07. Attack Result

실행 차단, 승인 내용과 실제 실행 요청의 차이, 승인 3 / 3, 실행 검증 FAIL을 표시한다.

## FE-08. Security Detail

기본적으로 접어 두고 필요할 때 다음을 표시한다.

- Threshold: PASS
- Intent: PASS
- Expiration: PASS
- Execution Match: PASS 또는 FAIL

# 22. 개발 완료 기준

### Happy Path

- 5명의 Owner가 존재한다.
- 3명의 승인이 필요하다.
- 공동계좌에 자산을 입금할 수 있다.
- 지출 Proposal을 생성할 수 있다.
- 3명의 Owner가 승인할 수 있다.
- 정상적인 Execution이 성공한다.

### Security

- 승인된 Intent가 Hash로 결속된다.
- 실행 전에 Transaction과 Intent를 비교한다.
- Recipient가 변경되면 실행되지 않는다.
- Threshold가 충족돼도 Mismatch이면 실행되지 않는다.

### Demo

- 동일한 UI에서 Happy Path를 보여줄 수 있다.
- 동일 Proposal 구조에서 Attack Path를 재현할 수 있다.
- Attack이 실제로 Contract에서 차단된다.
- 차단 이유를 Frontend에서 확인할 수 있다.

# 23. 최종 핵심 규칙

    3 Approvals
    AND Valid Intent
    AND Matching Execution
    = Execute

즉, 3 Approvals AND Intent Mismatch = BLOCK.

**승인 수가 충분하더라도 합의한 내용과 다른 거래는 실행하지 않는다.**
