# 1. 프로젝트 개요

### 서비스명

**Moa(모아)**

### 한 줄 소개

> **함께 모으고, 함께 결정하는 공동계좌**

Moa는 여러 사람이 공동으로 자산을 모으고, 정해진 수 이상의 구성원이 동의해야 자산을 사용할 수 있도록 하는 **멀티시그 기반 공동자산 관리 서비스**다.

사용자에게는 일반적인 공동계좌처럼 보이지만, 내부적으로는 단순히 서명 수만 확인하지 않고 **구성원이 승인한 내용과 실제 실행될 거래가 동일한지 검증하는 보안 계층**을 함께 가진다.

---

# 2. 개발 목표

이번 개발의 목표는 크게 두 가지다.

### 2.1 멀티시그의 실제 사용 경험 구현

블록체인이나 멀티시그에 익숙하지 않은 사용자도 다음 과정을 자연스럽게 사용할 수 있도록 한다.

```
공동계좌 생성
→ 자금 입금
→ 지출 제안
→ 구성원 승인
→ Threshold 충족
→ 지출 실행
```

사용자가 `3-of-5`, `Threshold`, `Multisig` 등의 기술 용어를 알 필요는 없다.

예를 들어 `3-of-5`는 UI에서 다음과 같이 표현한다.

> **5명 중 3명이 동의하면 사용할 수 있어요.**

### 2.2 승인 의도와 실제 실행의 불일치 방어

멀티시그는 필요한 수 이상의 유효한 서명이 존재하는지는 검증할 수 있지만, 사용자가 보거나 승인한 내용과 실제 실행되는 거래의 의미가 일치하는지까지 항상 보장하는 것은 아니다.

Moa에서는 지출 제안 시 승인 조건을 별도의 **Intent**로 정의하고, 실제 실행 직전에 Intent와 Transaction을 다시 비교한다.

```
사용자가 승인한 내용
        ↓
      Intent
        ↓
  3-of-5 승인
        ↓
실제 실행 요청 생성
        ↓
Intent와 Execution 비교
        ↓
일치 → 실행
불일치 → 차단
```

이번 프로토타입에서는 특히 **Bybit형 표시·승인 내용과 실제 실행 데이터의 불일치**를 Attack Path로 구현한다.

# 3. 대표 사용 시나리오

Moa는 데이트통장, 가족 공동자산, 동아리 회비 등으로 확장할 수 있지만, 이번 MVP와 발표에서는 **친구 5명의 여행 통장**을 대표 시나리오로 사용한다.

### 참여자

- 정연한
- 최승원
- 정윤호
- 김다헌
- 유태연

### 계좌 설정

```
제주도 여행

참여자
5명

필요한 동의
3명

→ 3-of-5 Multisig
```

각 구성원이 공동자금을 입금하고, 중요한 지출은 5명 중 3명 이상이 동의해야 실행할 수 있다.

# 5. Happy Path

발표 전반부에서 보여주는 기본 사용자 경험이자 개발의 첫 번째 Acceptance Path다.

## STEP 1. 공동 자금 조성

예:

```
제주도 여행

현재 잔액
1,000,000원

연한    200,000
승원    200,000
윤호    200,000
다헌    200,000
태연    200,000
```

실제 구현에서는 테스트넷의 Native Token 또는 ERC-20 테스트 토큰을 사용한다.

UI에서는 필요할 경우 원화 환산값 형태로 추상화한다.

## STEP 2. 지출 제안

한 명의 구성원이 새로운 지출을 제안한다.

예:

```
제주도 숙소

금액
320,000원

받는 곳
Hotel A

유효기간
10월 5일까지
```

이때 단순 Transaction만 만드는 것이 아니라 Moa 내부적으로 **Intent**를 생성한다.

# 6. Intent 정의

Intent는 사용자의 심리적인 의도가 아니라, 구성원들이 명시적으로 승인하는 **거래 조건의 집합**이다.

MVP에서는 다음 정보를 포함한다.

```
Intent

purpose
제주도 숙소

recipient
0xHotel...

amount
320,000

action
TRANSFER

expiresAt
2026-10-05 23:59

nonce
1
```

필요한 핵심 조건은 다음과 같다.

- 대상 주소
- 금액
- 행위 유형
- 유효기간
- 계좌/Proposal 식별자
- nonce

Intent 전체를 정규화한 뒤 Hash를 생성한다.

```
Intent
↓
Intent Hash
↓
Signer Approval
```

# 7. 구성원 승인

다른 사용자들은 Proposal 상세 화면에서 거래를 확인한다.

```
제주도 숙소
320,000원

받는 곳
Hotel A

────────────────

연한    동의 ✓
승원    동의 ✓
윤호    대기
다헌    대기
태연    대기

2 / 3

[ 동의하기 ]
```

세 번째 사용자가 승인하면:

```
연한    ✓
승원    ✓
윤호    ✓
다헌    -
태연    -

3 / 3

지출할 수 있어요.
```

내부적으로는 동일한 Intent Hash에 대한 승인을 확인한다.

```
Intent Hash
0xA83F...

연한    ✓
승원    ✓
윤호    ✓

Threshold
3 / 5
```

# 8. 정상 실행

Threshold가 충족되면 Transaction 실행이 가능하다.

하지만 바로 실행하지 않고 다음 검증을 수행한다.

```
Threshold Check      ✓
Intent Check         ✓
Expiration Check     ✓
Execution Match      ✓
```

모든 검증을 통과한 경우에만 실제 자산을 이동한다.

사용자에게는 복잡한 검증 과정 대신 다음 정도만 보여준다.

```
3명이 동의했어요.

지출이 완료되었습니다.

제주도 숙소
320,000원
```

# 9. Attack Path

발표 후반부에서는 동일한 Moa와 동일한 거래를 다시 사용한다.

이번에는 Bybit 사례와 유사하게 **사용자가 승인한 내용과 실제 실행될 내용 사이의 불일치**를 발생시킨다.

## 9.1 정상 승인

구성원들이 본 내용:

```
제주도 숙소

Recipient
0xHOTEL

Amount
320,000
```

세 명이 정상적으로 승인한다.

```
연한 ✓
승원 ✓
윤호 ✓

3 / 3
```

Threshold 자체는 정상적으로 충족된다.

## 9.2 공격 발생

실행 단계에서 Transaction payload가 다음과 같이 변조된다.

### 승인된 Intent

```
Recipient
0xHOTEL

Amount
320,000
```

### 실제 Execution Request

```
Recipient
0xATTACKER

Amount
320,000
```

단순 Threshold 기준으로 보면:

```
Required Approvals
3

Collected Approvals
3

→ 통과
```

하지만 Moa의 Security Layer는 Intent와 Execution을 비교한다.

```
Expected Recipient
0xHOTEL

Actual Recipient
0xATTACKER

→ MISMATCH
```

따라서 실행한다.

```
EXECUTION BLOCKED
```

# 11. CoC Activity Log

각 Proposal에서는 승인부터 실행까지 주요 이벤트를 기록한다.

예:

```
10:31
지출 제안 생성

10:32
연한 승인

10:33
승원 승인

10:34
윤호 승인

10:34
Threshold 충족

10:35
Transaction 실행 요청

10:35
Intent / Execution mismatch 감지

10:35
실행 차단
```

Happy Path에서는:

```
10:35
Intent / Execution 일치

10:36
Transaction 실행 완료
```

형태가 된다.

이 기록은 사용자에게는 **활동 내역**으로 제공하고, 발표 후반에는 승인 과정의 CoC 기록이라는 관점에서 다시 설명한다.

# 13. Smart Contract 방향

이번 프로토타입에서는 **자체 Multisig Contract 구현을 우선한다.**

Safe를 직접 연동하는 방식보다 실제 운영 환경과의 연결성은 낮지만, 짧은 개발 기간 동안 다음 핵심 메커니즘을 명확하게 검증하기에 적합하다.

- M-of-N 승인
- Intent 결속
- Threshold 검증
- Execution Validation
- Attack Path 재현

예상 인터페이스는 다음과 같다.

```
create / deploy account

deposit()

proposeTransaction()

approveTransaction()

executeTransaction()

getProposal()

getApprovals()
```

필요할 경우 Intent Hash 생성 및 validation을 별도 함수로 분리한다.

# 16. Backend 역할

Backend는 보안의 최종 Enforcement 계층이 아니다.

최종 자산 실행 조건은 Smart Contract에서 검증한다.

Backend는 사용자 경험을 위한 데이터를 담당한다.

주요 역할:

- 공동계좌 메타데이터
- Proposal 설명
- 목적 등 사용자 친화적 정보
- Activity Log
- Transaction 상태 캐싱
- 이벤트 인덱싱
- 필요 시 알림

Backend가 변조되더라도 직접 자산 실행 조건을 우회할 수 없도록 구성하는 것을 원칙으로 한다.

이번 프로젝트에서 가장 높은 우선순위는 **컨트랙트 Happy Path**다.

### 1단계

```
3-of-5 Account
→ Deposit
→ Proposal
→ Approval
→ Execute
```

완성.

### 2단계

```
Intent
→ Approval Binding
→ Execution Match
```

추가.

### 3단계

```
Malicious Payload
→ Mismatch
→ BLOCKED
```

Attack Path 완성.

### 4단계

FE/BE 및 발표용 UX 개선.

# 21. 개발 Acceptance Criteria

## Happy Path

Given:

- 5명의 owner가 등록되어 있고
- Threshold가 3이며
- 충분한 잔액이 존재한다.

When:

- 유효한 Proposal을 생성하고
- 서로 다른 3명의 owner가 동일 Proposal에 승인하고
- 승인된 Intent와 동일한 Transaction을 실행한다.

Then:

```
Threshold = PASS
Intent = PASS
Execution Match = PASS

→ Transaction executed
```

## Attack Path

Given:

- 3명의 owner가 정상적인 Proposal에 승인했다.

When:

- 실행 단계의 Recipient 또는 다른 핵심 Transaction 값이 승인된 Intent와 달라진다.

Then:

```
Threshold = PASS
Intent Approval = PASS

Execution Match = FAIL

→ Transaction blocked
```

**Threshold가 충족되었어도 실행되어서는 안 된다.**

이 조건이 이번 프로젝트의 가장 중요한 보안 Acceptance Criteria다.

# 22. 발표와 개발 결과물의 관계

Moa의 전체 보안 기능은 처음부터 구현되어 있지만 발표에서는 단계적으로 공개한다.

## 첫 번째 데모 — Happy Path

보여주는 내용:

```
공동계좌
→ 지출 제안
→ 3-of-5 승인
→ 실행
```

목표:

> 청중에게 멀티시그가 무엇인지 직관적으로 이해시킨다.

## 리서치

다룰 내용:

- Bybit
- Humanity
- Drift
- 독립 방어선
- 승인 의도의 CoC

목표:

> 여러 서명이 있다는 사실만으로 올바른 공동 승인이 보장되는 것은 아니라는 점을 보여준다.

## 두 번째 데모 — Attack Path

처음 사용한 것과 동일한 Moa와 Proposal을 다시 사용한다.

```
3-of-5 승인
        ↓
Transaction 변조
        ↓
Threshold ✓
        ↓
Execution Match ✕
        ↓
BLOCKED
```

이때 처음 숨겨두었던 Security Layer를 공개한다.

# 23. 프로젝트 핵심 메시지

Moa의 개발 결과를 한 문장으로 표현하면 다음과 같다.

> **Moa는 여러 사람이 함께 자산을 관리하는 멀티시그 서비스이며, 단순히 충분한 서명이 모였는지만 확인하지 않고 실제 실행이 구성원들이 합의한 내용과 동일한지도 검증한다.**

발표 전체에서는 이를 다음 질문으로 확장한다.

> **여러 사람이 서명했다는 사실만으로 정말 공동의 승인이 만들어졌다고 할 수 있을까?**

개발은 멀티시그가 **어떻게 사용될 수 있는지** 보여주고, 리서치는 멀티시그가 **어떻게 실패할 수 있는지** 보여준다.

그리고 마지막 Attack Path를 통해 두 결과를 하나로 연결한다.
