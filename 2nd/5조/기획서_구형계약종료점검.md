# 구형 계약 종료 점검: Notional V1의 형 변환 코드와 남은 함수 목록 확인

> 「구형 계약 종료 점검」은 지원이 끝난 스마트 컨트랙트(블록체인 위에서 자동으로 실행되는 프로그램)에 무엇이 남아 있는지 직접 확인하는 BAY 정규세션 팀 프로젝트입니다.
> 대상은 Notional V1의 공개 코드·ABI와 종료 관련 자료입니다. 공격을 재현하거나 실제 자금을 움직이는 작업은 하지 않습니다.
> 결과물은 경계값 테스트 1개, 함수 분류표 1개, 저장 구조 비교표 1개이며, 아티클 「스마트 컨트랙트의 보안 관리는 언제 끝나는가」의 근거 자료로 씁니다.

## 1. 프로젝트 개요

### 1.1 제목과 한 줄 설명

- **제목:** 구형 계약 종료 점검
- **한 줄 설명:** 지원이 끝난 Notional V1 컨트랙트에서 숫자 변환이 어디서 깨지는지, 그리고 어떤 함수가 남아 있었는지 공개 자료로 점검합니다.

### 1.2 배경 (확인된 사실)

Notional은 이더리움 위의 고정금리 대출 서비스입니다. 2021년 12월 공지에서 V1 지원을 2022년 1월 31일에 끝낸다고 알렸습니다. 다만 출금에는 마감 기한을 두지 않았습니다. [V1 종료 공지](https://blog.notional.finance/notional-v1-deprecation-notice/)

2026년 9월, V1 Escrow(예치 자산 보관 계약)에서 약 173만 달러(약 165만 USDC, 약 6.9만 DAI)가 빠져나갔습니다. 공격 대상은 V1에 남아 있던 사용자 자산이었습니다. 사고 후 Notional은 V1의 모든 동작을 멈추도록 업그레이드했고, 앞으로 버전을 종료할 때는 자산 이전·반환까지 포함하겠다고 밝혔습니다. [공식 사후 보고서](https://blog.notional.finance/notional-v1-exploit-post-mortem/)

공격 방식은 외부 분석을 인용합니다. 만기가 다른 두 부채(수량 1과 2¹²⁸ − 1)의 합계 절댓값이 정확히 2¹²⁸이 되었고, 이 값을 더 작은 정수 타입으로 바꾸는 과정에서 0으로 잘렸습니다. 그 결과 담보 검사에서 부채가 0으로 계산되었고, 담보 없는 청구권을 이용해 실제 토큰을 인출했습니다. fCash는 만기에 받을 돈 또는 갚을 의무를 나타내는 기록입니다. [SlowMist 분석](https://slowmist.medium.com/the-vanishing-debt-an-analysis-of-the-notional-finance-hack-a79b00fa2e47) · [QuillAudits 분석](https://www.quillaudits.com/blog/hack-analysis/notional-finance-integer-overflow-exploit)

관련 형 변환은 과거 감사에서도 지적됐습니다. OpenZeppelin은 2020년 12월 감사에서 안전하지 않은 형 변환을 L10(낮은 심각도)으로 보고하고 SafeCast(범위를 먼저 확인하는 변환 도구) 사용을 권했습니다. [OpenZeppelin 감사 보고서](https://www.openzeppelin.com/news/notional-audit)

### 1.3 코드에서 직접 확인한 점

사전 조사에서 GitHub 공개 코드 [ExchangeRate.sol](https://github.com/notional-finance/contracts/blob/master/contracts/utils/ExchangeRate.sol)을 2026-10-05에 확인했습니다. _convertToETH와 _convertETHTo 두 함수에 uint128 absBalance = uint128(balance.abs()); 줄이 있습니다. 즉 int256 값의 절댓값을 **uint128**(부호 없는 128비트 정수)로 바로 바꿉니다.

같은 함수의 계산 결과에는 SafeCast.toUint128을 쓰지만, 입력값 변환에는 쓰지 않습니다. 결과를 검사하기 전에 입력의 상위 비트가 잘릴 수 있는 구조입니다.

파일의 컴파일러 지시는 pragma solidity ^0.6.0입니다. Solidity의 명시적 형 변환은 큰 정수 타입을 작은 타입으로 바꿀 때 상위 비트를 버립니다. 0.8부터 들어온 산술 오버플로 검사도 이런 명시적 축소 변환을 자동으로 막지는 않습니다. [Solidity 명시적 변환 문서](https://docs.soliditylang.org/en/latest/types.html#explicit-conversions) · [0.8 변경 사항](https://docs.soliditylang.org/en/latest/080-breaking-changes.html#silent-changes-of-the-semantics)

1주차에는 분석할 GitHub 커밋을 고정하고, 공개 코드와 사고 당시 배포 코드가 일치하는지 확인합니다. 형 변환 표기는 “int256 절댓값 → uint128”로 통일합니다.

### 1.4 문제의식

“지원 종료일”이 지나면 보안 관리도 끝난다고 보기 쉽습니다. 하지만 V1에는 지원이 끝난 뒤에도 자산과 실행 가능한 기능이 남아 있었습니다. 저희는 종료를 날짜가 아니라 **남은 자산·의무, 호출 가능한 함수, 남은 권한**으로 판단해야 한다고 봅니다.

### 1.5 왜 필요한가

현재 아티클 초안은 경계값 테스트를 “직접 실행하지 않았다”고 적고 있습니다. 이 부분을 실제 테스트 결과로 보강하려고 합니다. 함수 목록과 저장 구조 비교는 “종료할 때 무엇을 점검해야 하는가”를 구체적인 표로 보여줄 수 있다고 봅니다.

### 1.6 핵심 질문

**출금을 남길 때, 새 청구권을 만드는 함수는 얼마나 줄일 수 있는가?**

이 프로젝트에서는 함수 목록과 코드 검토를 통해 제한을 검토할 후보를 찾습니다. 출금·정산과 신규 생성이 같은 내부 기능을 사용하는지도 함께 확인합니다. 실제로 기능을 막은 계약을 배포하는 단계까지 진행하지 않으므로, 결과는 제한 후보와 필요한 후속 검증으로 정리합니다.

공격 단계 설명은 공식 보고서와 외부 분석의 인용으로 두고, 팀이 직접 확인한 결과와 구분합니다.

## 2. 목표와 범위

### 2.1 만들 것 / 확인할 것

- 형 변환 경계값을 확인하는 Foundry 테스트 1개(여러 입력 사례를 포함한 테스트 묶음)
- V1 공개 ABI(계약의 외부 함수와 입출력 형식을 적은 명세)를 읽어 함수 목록을 추출하는 스크립트와 분류표
- 업그레이드 전후 저장 구조(storage layout)를 비교하는 스크립트와 표

1주차에 대상 계약 주소, 사고 전 구현체, 분석 기준 블록과 소스 버전을 정합니다. 현재 ABI와 사고 당시 ABI를 구분하고, 필요한 연결 계약은 대상 목록에 추가합니다.

### 2.2 다루지 않는 것

- 실제 자금을 움직이는 거래와 공격 전체 재현
- 메인넷 포크(실제 체인 상태를 복사한 테스트 환경)에서 자금을 옮기거나 빼내는 경로
- 공격 재현 스크립트와 익스플로잇 코드
- Notional의 실제 계정 상태나 실제 만기 데이터를 넣은 테스트
- 운영에 사용할 종료 계약의 배포

이번 프로젝트는 숫자 변환, 함수의 역할, 저장 구조에 집중합니다. 이 범위에서 확인한 결과를 바탕으로 종료 시 점검할 항목을 제시합니다.

## 3. 산출물 세 가지

### 3.1 산출물 1: 경계값 변환 테스트 (Foundry)

- **목적:** 큰 정수를 작은 타입으로 바꿀 때 언제 0이 되거나 잘리는지, 그리고 변환 전 범위 검사가 이를 어떻게 거부하는지 보여줍니다.
- **입력:** 0, 1, 2¹²⁸ − 2(최댓값 바로 아래), 2¹²⁸ − 1(최댓값), 2¹²⁸(범위 바로 위), 2¹²⁸ + 1을 사용합니다. 해당 크기의 음수 입력과 부채 합산 사례도 포함합니다.
- **방법:**
  1. 원 코드의 절댓값 처리와 uint128 변환을 따라 만든 최소 테스트에서 결과를 기록합니다.
  2. 비교 경로에서는 절댓값이 음수가 아닌지 확인하고 uint256으로 바꾼 뒤, 호환되는 OpenZeppelin SafeCast의 toUint128을 적용합니다.
  3. int256에서 −1과 −(2¹²⁸ − 1)을 더한 뒤 절댓값을 변환하는 경우를 넣습니다. 각 값의 크기는 uint128 범위에 있지만 합계 절댓값은 범위를 넘는 사례입니다.
  4. 가능하면 0.6과 0.8 컴파일러에서 모두 실행합니다. 두 환경의 컴파일러·SafeCast 버전과 변환 구문을 각각 기록하고, 의존성을 분리합니다.
- **예상 출력·기록 형식:** forge test -vv 로그 원문과 “입력값 | 일반 변환 결과 | SafeCast 결과(값 또는 revert)” 표. 테스트 코드·설정·실행 명령도 함께 보관합니다.
- **완료 기준:** 입력별 기대값과 실제값이 일치하고, 범위 밖 입력은 예상한 검사 단계에서 거부돼야 합니다. 다른 팀원이 같은 설정으로 재실행할 수 있어야 합니다.
- **뒷받침하는 주장:** “합계 절댓값이 2¹²⁸이면 uint128 변환에서 0으로 잘린다”, “변환 전 범위 검사는 해당 입력을 거부한다”.

일반 변환에서 2¹²⁸은 0, 2¹²⁸ + 1은 1로 잘릴 것으로 예상합니다. 예상값은 실행 결과와 대조하며, 아직 확인한 결과로 쓰지 않습니다. 최소 숫자 테스트만으로 전체 공격이 차단된다고 결론 내리지는 않습니다.

### 3.2 산출물 2: 공개 ABI 함수 분류표

- **목적:** V1 코드에 어떤 함수가 있었는지, 그중 무엇이 새 권리·의무를 만드는지 보여줍니다.
- **입력:** 사고 전 구현체에 대응하는 검증 ABI 또는 고정한 GitHub 코드로 컴파일한 ABI. 계약 주소·버전·출처를 함께 기록합니다.
- **방법:** Python 또는 Node 스크립트로 함수 목록을 추출하고, 소스 검토를 통해 다음 네 가지로 분류합니다.
  - 출금 / 정산·상환 / 신규 포지션·청구권 생성 / 기타·관리자
  - 기준은 화면 버튼 이름이 아니라 **상태 변화**입니다. 내부 함수와 연결 계약을 확인해 새 권리·의무가 생기는지 살펴봅니다.
  - 출금과 신규 생성이 같은 내부 경로를 사용하는 함수는 복수 분류하고 관계를 메모합니다.
  - 이름만으로 판단하기 어려운 함수는 “수동 호출 경로 검토 필요”로 표시합니다.
- **예상 출력·기록 형식:** CSV와 Markdown 표(계약·버전 | 전체 함수 서명 | 분류 | 접근 조건·근거 | 수동 검토 여부), 분류별 개수 요약. 복수 분류는 개수 집계 시 별도로 표시합니다.
- **완료 기준:** 대상 ABI의 모든 함수가 분류표에 있고, 근거 코드 위치와 검토 메모가 있어야 합니다. fallback·receive 및 프록시 전달 경로도 해당하는 경우 별도로 기록합니다.
- **뒷받침하는 주장:** 출금 유지에 필요한 기능과 신규 청구권 생성의 제한 후보를 구분할 수 있다는 점.

ABI는 목록 추출의 출발점입니다. 함수의 역할과 접근 조건은 소스로 확인하며, ABI에 존재한다는 이유만으로 사고 당시 실행 가능했다고 쓰지 않습니다. 과거 구현체를 확인하지 못한 경우에는 “공개 소스 기준”으로 표기합니다.

### 3.3 산출물 3: 업그레이드 전후 저장 구조 비교

- **목적:** 기능을 제한한 구현체로 바꿀 때 기존 값의 저장 위치와 해석이 어긋나는지 점검하는 방법을 보여줍니다.
- **입력:** V1 구현 코드와 팀이 만든 제한 후보 구현 코드. 팀 구현은 로컬 비교용이며, 사고 당시 Notional이 적용한 구현체나 운영용 종료 계약과 구분합니다.
- **방법:** forge inspect의 storageLayout 또는 solc의 저장 구조 출력을 JSON으로 추출해 비교합니다. 슬롯 번호·슬롯 안 오프셋·타입·순서와 상속에 따른 배치를 확인합니다. 구조체·매핑·배열의 타입 정보도 함께 봅니다. 판단 기준은 [OpenZeppelin 업그레이드 안전 가이드](https://docs.openzeppelin.com/upgrades-plugins/writing-upgradeable#modifying-your-contracts)입니다.
- **예상 출력·기록 형식:** 원본 저장 구조 JSON, 비교 스크립트 실행 로그, “변수 | 이전 슬롯·오프셋·타입 | 이후 슬롯·오프셋·타입 | 판정” 표.
- **완료 기준:** 저장 구조를 유지한 예시에서는 일치를, 의도적으로 순서나 타입을 바꾼 예시에서는 불일치를 확인해야 합니다. 컴파일러 버전과 비교 대상 코드를 함께 보관합니다.
- **뒷받침하는 주장:** 종료를 위해 코드를 수정할 때에도 기존 사용자 잔액과 소유자 정보의 저장 구조를 확인해야 한다는 점.

저장 구조가 같다는 결과만으로 기능·권한·초기화까지 안전하다고 판단하지 않습니다. V1의 컴파일 환경을 확보하지 못하면 최소 예제로 비교 방법을 확인하고, 실제 V1 저장 구조를 검증한 결과와 구분합니다.

### 3.4 결과 섹션 작성 원칙

최종 보고서에는 실제 실행한 테스트와 비교 로그, 검토한 소스·ABI와 그 근거를 기록합니다. 아직 테스트와 스크립트를 실행하지 않았으므로, 이 기획서에는 방법과 예상 출력 형식만 적습니다.

최소 테스트, 공개 소스 분석, 실제 배포본 확인을 구분하고, 각각의 결과가 뒷받침할 수 있는 범위에 맞춰 아티클에 반영합니다.

| 3주차 | 산출물 2 수동 검토, 산출물 3 제한 후보와 비교 스크립트 작성·실행 | 분류표, 저장 구조 비교 로그 |
| 4주차 | 재실행·상호 검토, 이미지 제작, 보고서·아티클 반영 | 최종 보고서, 아티클 수정본, 별도 PNG |

1주차 종료 시 자료 확보와 컴파일 가능 여부를 확인합니다. 배포본을 확보하지 못한 부분은 공개 소스 기준으로, 저장 구조 비교가 어려운 부분은 최소 예제 기준으로 진행하고 결과에 범위를 표시합니다.

## 5. 역할 분담 (예시)

- **팀원 A:** Foundry 경계값 테스트와 실행 환경·로그 정리(산출물 1)
- **팀원 B:** ABI 수집과 함수 목록 추출 스크립트, 소스 기반 분류(산출물 2)
- **팀원 C:** 저장 구조 비교와 로컬 제한 후보 작성(산출물 3), 프록시 구조·구현체 확인
- **공통:** 사실 출처 확인, 이미지 제작, 아티클 반영. 한 사람이 작성한 결과는 다른 사람이 코드와 기록을 대조하거나 재실행해 검토합니다.

각 담당자는 요약뿐 아니라 원본 자료·코드·설정·실행 명령을 함께 전달합니다. 담당자 이름과 시작일은 팀에서 확정합니다.

## 6. 도구와 데이터

- **Foundry:** forge test로 테스트, forge inspect로 저장 구조 추출
- **solc:** 정확한 버전을 고정해 컴파일과 저장 구조 출력
- **OpenZeppelin SafeCast:** 컴파일러와 호환되는 버전을 고정해 변환 비교
- **Python 또는 Node:** ABI 함수 목록 추출, CSV·Markdown 표 생성, 저장 구조 비교
- **데이터 출처:** [Notional V1 GitHub 코드](https://github.com/notional-finance/contracts), 탐색기의 검증 코드·ABI·구현체 변경 기록(확보 여부는 1주차 확인)

분석에 사용한 소스 커밋, 계약 주소와 기준 블록, 도구·의존성 버전을 기록합니다. 실행 방법은 README에 정리합니다.

## 7. 보고서·아티클 연결

| 산출물 | 보고서 섹션 | 아티클에서 활용할 내용 |
| --- | --- | --- |
| 1. 경계값 테스트 | 결과 / 발견한 문제와 제약 | 숫자 변환이 잘리는 지점과 범위 검사 결과 |
| 2. 함수 분류표 | 결과 / 다음 단계 | 출금 유지에 필요한 기능과 신규 청구권 생성의 제한 후보 |
| 3. 저장 구조 비교 | 결과 / 발견한 문제와 제약 | 종료를 위해 수정할 때 보존해야 할 저장 값 |
| 1주차 확인 메모 | 진행 방식 / 제약 | 분석한 코드 버전과 배포본 확인 범위 |

최종 Medium 아티클에서는 필요한 표를 이미지로 제공합니다. 기획서에서는 Markdown 표로 둡니다. 진행 보고서에는 실제 수행 과정과 결과를, 아티클에는 주장에 필요한 결과만 선별해 반영합니다.

## 8. 리스크와 대응

| 리스크 | 대응 |
| --- | --- |
| V1 ABI·소스를 탐색기에서 확보하지 못함 | 고정한 GitHub 코드로 ABI를 만들고 “공개 소스 기준”으로 표시 |
| 과거 구현체와 변경 이력을 확인하기 어려움 | 현재 구현체와 구분해 기록하고, 사고 당시 실행 상태를 확정하지 않음 |
| 오래된 코드·의존성의 컴파일이 어려움 | 변환 테스트와 저장 구조 비교를 최소 예제로 진행하고 실제 V1 검증과 구분 |
| 함수 분류가 애매하거나 여러 역할을 가짐 | 복수 분류·수동 검토 표시와 내부 호출 근거를 남김 |
| 재현 작업으로 범위가 넓어짐 | 실제 상태·메인넷 포크·자금 이동 코드는 작성하지 않음 |
| 타입 표기가 혼재함 | 원 코드에 맞춰 int256 절댓값 → uint128로 통일 |
| 저장 구조 비교만으로 안전성을 과대평가함 | 기능·권한·초기화 검증과 별개의 결과로 설명 |

## 9. 사실과 해석 구분 원칙

- 사실은 출처 링크와 함께 씁니다(공지, 사후 보고서, 감사 보고서, 코드, 문서).
- 팀의 생각과 계획은 확인한 사실과 구분해 씁니다.
- 공격 과정은 공식 보고서와 외부 분석을 인용해 설명합니다.
- 팀 결과에는 실행 로그 또는 소스 검토 근거를 남깁니다.
- 예상 출력과 실제 결과, 최소 예제와 배포본 검증을 구분합니다.

## 10. 이미지 계획

모든 이미지는 16:9 비율을 기본으로 하고, BAY 색상 #02122F, #02295B, #08428B, #0A61E7, #129AF0, #E6F1FD를 사용합니다.

- **경계값 테스트 결과:** 입력값별 일반 변환 결과와 SafeCast의 값·거부 여부를 나란히 표시합니다. 큰 정수의 크기보다 변환 결과를 보여줍니다.
- **함수 분류 차트:** 네 분류별 함수 개수와 수동 검토·복수 분류를 표시합니다. 필요한 경우 주요 내부 호출 관계도 함께 보여줍니다.
- **저장 구조 비교 도식:** 업그레이드 전후 슬롯을 나란히 놓고 차이가 있는 칸을 강조합니다.
- **표 이미지:** 보고서·아티클에 필요한 표를 이미지로 변환하고 CSV·Markdown 원본도 보관합니다.

글자·수치·구조를 원본과 대조하고, 이미지는 직접 삽입할 수 있도록 별도 PNG 파일로 제공합니다.
