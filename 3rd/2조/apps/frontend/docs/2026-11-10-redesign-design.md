# Frontend 재설계 설계서

작성 2026-11-10, 수정 2026-11-11 · 담당 최현수(Henry) · 상태: Henry 승인(2026-11-11)

## 1. 왜 다시 만드는가

지금 `apps/frontend`는 화면 A~D를 탭 네 개로 나란히 둔 구조다. 실제로는 앞 단계의 결과(분석 ID, 결정 ID)가 다음 단계의 입력이라 사용자가 드롭다운으로 ID를 골라 넘겨야 하고, 화면은 결과 코드를 보여줄 뿐 "어떤 단계에서 왜 막혔고 그게 무슨 뜻인지"를 말해주지 않는다. Henry가 직접 써 보고 내린 평가는 "케이스 상세에 들어가면 전부 이게 무슨 말이지 싶다"였다. 겉모습도 흔한 AI 생성 UI처럼 보인다(카드 안의 카드, 배지 남발, IBM Plex).

목표는 **컴플라이언스 담당자가 송금 한 건을 넣으면 "막을지, 왜인지, 근거가 뭔지"를 자연어 문장으로 바로 이해하는 웹앱**이다. 용도는 학회 발표에서 보여주는 데모다. 공개 주소로 배포하지만 프로덕션이 아니고 상용화할 앱도 아니다(Henry, 2026-11-11).

## 2. 사용자

컴플라이언스 담당자(Henry 결정). KYT, 제재 스크리닝, OFAC SDN, 노출(exposure), 경보(alert) 같은 컴플라이언스 용어는 안다. 솔라나 내부 구조(토큰 계정과 소유자 지갑의 구분, 명령어 위치, 슬롯, pslice, attestation, 리더)는 모른다고 가정한다. 그래도 이 용어들은 **그대로 쓰고**, 옆에 `?` 아이콘을 두어 마우스를 올리면 뜻을 설명한다(Henry 결정, 7장).

담당자에게 중요한 것: 판정, 이유, 근거 거래, 그리고 감사 정보(어떤 정책·규칙 버전, 어떤 데이터, 언제).

## 3. 목표, 비목표, 안티골

**목표**

- G1. 메인 기능은 **송금 심사(판정)**: 두 지갑 탐지(A) + 거래 전 정책 결정(B) + 이유와 근거.
- G2. 모든 화면과 블록은 "무슨 질문에 답하는지"와 "답"을 쉬운 문장으로 먼저 말한다. 그림과 코드값은 그 문장을 뒷받침한다.
- G3. 실제 앱 흐름: 로그인 → 케이스 대시보드 → 새 케이스 → 케이스 화면.
- G4. 케이스를 저장하고 다시 열 수 있다. Backend가 재시작되어도 남는다.
- G5. 주소와 거래 서명은 외부 익스플로러(Solscan, Solana Explorer)로 연결된다. 합성 데이터는 연결하지 않는다(6장).
- G6. Gateway 실험(C)과 Constellation 실험(D)은 케이스 화면의 **"시뮬레이션" 버튼 → 다이얼로그**로 연다.
- G7. 영어로 먼저 만들고, 처음부터 번역 구조를 둬서 한국어는 문구 사전만 추가하면 되게 한다.
- G8. Notion 04 "6. 완료 조건" 8개를 모두 유지한다(11장 대응표).

**비목표**

- 담당자가 판정을 바꾸는 처분 워크플로(승인/반려/메모). Backend에 API가 없고 스펙에도 없다.
- 다중 홉 자금 추적. KYT 범위가 직접 상대방까지다(contracts/semantics.md).
- 실제 송금, 컨트랙트 배포, 공통 계약(contracts/) 변경.
- 모바일 전용 설계. 반응형 기본(폰 폭에서 가로 스크롤 없음)만 지킨다.
- 프로덕션 운영: 접근 제어, 사용자 관리, 보안 강화, 확장성. 발표용 데모다.

**안티골 (기능이 돌아가도 실패로 본다)**

- 프론트가 위험도, 정책 Action, 시뮬레이션 결과를 계산하거나 다시 해석한다.
- 합성 Fixture 주소·서명을 실제 익스플로러에 연결해 실제 기록처럼 보이게 한다.
- 코드값(SANCTION_EXACT, POLICY_NOT_ENFORCED 등)만 늘어놓고 뜻을 말하지 않는다.
- 1~4단계를 한 페이지에 같은 무게로 나열한다.
- 화면 전환 같은 장식 애니메이션. 흔한 AI UI 느낌(IBM Plex, 카드 안 카드, 모든 값이 배지).

## 4. 제약

- Frontend는 Backend **Public API 6개만** 호출한다. `contracts/`가 단일 기준이며, 요청·응답을 계약 스키마로 검증하는 현재 구조(`src/api/contract.ts`, `client.ts`)는 유지한다.
- Backend(`baypeline/be`): 인증 없음, 분석·심사 기록은 메모리 저장(재시작 시 사라짐), "케이스" 개념 없음, Constellation 모델 버전 목록 API 없음. Collector가 아직 없어 LIVE 분석은 실패한다.
- Fixture는 모두 합성이고 시나리오당 거래 0~3건이다. Mock API는 송신자 `sender` × 수신자 시나리오, 정책 1.0.0 조합만 응답한다.
- 표시 의무(공통 계약·Notion 04): `riskScore: null`은 0이 아님, LOW는 안전 보증 아님, 합성/온체인 구분, Gateway는 실제 전송 없음(`actualBroadcast: false`), Constellation은 메인넷 결과 아님.
- 기존 코드: `apps/frontend`(Vite 8, React 19, TypeScript 7, MSW 3, Ajv), `feat/frontend` 브랜치, 아직 커밋 안 함. 계약 검증·Mock Backend·수량 변환·테스트 177개는 재사용한다.

## 6. 화면

### 6.1 로그인

실제 앱처럼 로그인 화면에서 시작하지만, 외부 인증 서비스는 쓰지 않는다(9장). 이름이나 이메일을 넣고 들어가면 대시보드가 열린다. 로그인 화면에 "오프체인 연구용 데모, 실제 송금 없음, 위험 신호는 법적 제재 판단이 아님"을 한 줄로 둔다.

### 6.2 케이스 대시보드 (심사 목록)

- 질문: "지금까지 심사한 송금은 어떻게 판정됐나?"
- 맨 위: 판정 분포 막대(Allow / Warn / Review / Block, 상태색 + 아이콘 + 글자).
- 목록 한 줄 = 케이스 하나: 케이스 ID, 송금(보내는 지갑 → 받는 지갑, 각 지갑의 identicon, 수량), **판정**, **이유**(reason code 문장 전부를 같은 무게로, 길면 말줄임), 두 지갑 위험도, 데이터 출처(합성/온체인), 시각.
- 판정별 필터, 주소·서명·케이스 검색. 줄을 누르면 케이스 화면.
- 3~4단계 결과는 대시보드에 넣지 않는다(메인이 아니므로).

### 6.3 새 케이스

- 송금 입력: 보내는 주소, 받는 주소, 자산(SOL / SPL / Token-2022, mint·decimals), 수량(십진 입력 → amountRaw 문자열 변환, Number 금지).
- 데이터 출처: LIVE(온체인) / FIXTURE. FIXTURE는 시나리오를 고르면 주소와 조회 기간이 채워진다. 조회 기간·최대 거래 수·정책 버전은 접힌 고급 설정.
- "Run case"를 누르면 프론트가 Public API를 순서대로 부른다: 송신자·수신자 분석(POST /analyses ×2, 상태 폴링) → 정책 심사(POST /compliance/evaluate). 기다리는 동안 단계별 진행과 dither 로딩을 보여준다. 끝나면 케이스 화면으로 간다.
- 실패(FAILED, 409, 422, 연결 실패)는 어느 단계에서 왜 멈췄는지 문장으로 보여주고, 재시도 가능하면 재시도 버튼을 둔다.

### 6.4 케이스 화면 (판정)

2026-11-11에 Henry 피드백으로 다시 짰다("어디부터 봐야 할지 모르겠다", "쓸데없는 글이 많다"). 크기가 곧 중요도다.

1. **판정**(가장 큼): 페이지 제목이 곧 결과다. "This transfer is blocked." / "is allowed." / "needs a confirmation first." / "is held for review."
2. **이유**(그다음 크기): 정책 reason code를 문장으로. 여러 개면 **전부 같은 무게로** 나열한다. Policy Engine은 reason code를 알파벳순으로 돌려주므로 순서에 의미가 없고, 프론트가 순위를 매기면 정책을 다시 해석하는 셈이 된다.
3. **작은 한 줄들**: 위쪽에 송금(줄인 주소 → 수량 → 줄인 주소)과 데이터 종류("Synthetic test data, not on chain"). 아래쪽에 위험도와 그 근거, 그리고 버튼 하나.
   - 위험도는 받은 점수와 등급을 쓰고, 각 지갑 분석이 보고한 규칙별 기여("Recipient: Sanctioned address +100")를 **받은 그대로** 옆에 둔다. 프론트가 더하거나 등식으로 쓰지 않는다.
   - 점수가 null이면 "Not scored"와 "0점이 아님"을, LOW면 "안전 보증이 아님"을 이 줄에 둔다.
4. **Evidence**: 제목은 한 단어. 부제 질문은 없다. 근거마다 **그 지갑이 한 일을 한 문장**으로 쓴다. 예: "제재 주소 2곳과 3건 거래: 2건 받음, 1건 보냄", "13:10:00~13:13:30 사이 서로 다른 지갑 6곳으로 6건". 숫자는 KYT가 근거로 든 거래를 센 것이고, 프론트가 판단하는 것은 없다. 분석이 보고한 기여 점수가 큰 근거를 먼저 둔다. 거래 표는 한 번 눌러야 열린다.
   - 상대 지갑이 둘 이상이면 근거 아래에 자금 흐름 그림을 둔다. 근거 거래는 굵은 선으로, DIRECT_FLOW 근거가 든 거래의 상대는 빨간 고리와 "Listed counterparty"로 표시한다. Public API는 어느 주소에 레이블이 붙었는지 돌려주지 않는다. 규칙 정의상 그 거래는 분석 대상과, 지갑이나 그 토큰 계정이 목록에 있는 상대 사이의 거래이므로 표시는 상대 단위다(소유자를 모르면 토큰 계정).
5. **접어 둔 세 줄**(기본으로 닫힘): Wallet analysis(지갑별 점수, 걸린 규칙, 분석한 데이터 범위), Transfers(자금 흐름과 타임라인), Audit(버전, 데이터 출처, ID, 원래 코드). 판정을 설명하는 정보가 아니라 확인하려는 사람이 찾는 정보다.
   - 자금 흐름 그림은 Evidence에 있다(상대 지갑이 둘 이상일 때만). Transfers에는 같은 내용의 한 문장과 타임라인을 둔다.
   - 주소는 줄여서 보여주고 복사 버튼을 둔다.
6. **버튼 "What if it's sent another way?"** → 6.5 다이얼로그. 네 판정 모두에 맞는 이름이어야 한다.

### 6.5 시뮬레이션 다이얼로그 (3~4단계)

케이스의 intentId·decisionId로만 호출한다. 맨 위에 한 문장만 둔다: "판정은 이 앱을 거치는 송금에만 적용된다." 두 탭:

- **Another route (Gateway)**: 실행 버튼이 없다. 다이얼로그를 열면 바로 실행하고, 저장된 결과가 있으면 그것을 보여준다("Run again"은 작은 글자 버튼).
  - 경로마다 한 줄의 **그림**: Transfer → 경로의 제출 단계 → Network. 실행할 때마다 송금 점이 선을 따라 한 번 움직이고, 경로가 막으면 제출 단계에서 멈춘다(그 뒤 구간과 Network는 흐리게). 옆에 결과 한 단어("Stopped" / "Held for review" / "Submitted")와 이유 한 줄.
  - 결론 문장은 점이 다 움직인 뒤에 나타난다.
  - 이 움직임은 방금 실행한 결과에만 한 번 나온다. 이미 저장된 결과(다이얼로그를 다시 열거나 탭을 바꿀 때)는 끝난 상태로 바로 보여준다.
  - 칸들 위에 결론 한 문장을 둔다(예: "판정은 이 앱 안에서만 유효하다. 정책을 건너뛰는 경로는 여전히 제출한다"). 이 문장은 받은 outcome의 조합을 사전으로 옮긴 것이며, 프론트가 판정하지 않는다.
  - 문구는 한 줄: "시뮬레이션이며 아무것도 전송하지 않는다."
- **On the network (Constellation)**: 질문 "경로가 제출한 뒤에도 블록 리더가 뺄 수 있나?"와 맥락 한 문장(지금은 리더 하나가 블록을 만들고 뺄 수 있다, Constellation은 증명이 충분하면 포함을 강제하는 제안이다).
  - 입력 폼 대신 **시나리오 버튼 3개**(증명 100%, 증명 30%, 모든 제안자가 거절). 버튼 이름은 입력만 말한다. 누르면 그림과 두 모델의 결과 문장이 바뀐다. 결과 문장은 Simulator가 돌려준 outcome과 explanationCodes다. 임계값은 프론트가 모른다.
  - 모델마다 그림을 하나씩 그린다. 그림은 보낸 시나리오와 **Simulator가 결과로 돌려준 단계만** 그린다: 제출 경로는 `proposerPathAvailable`일 때, 제안자 묶음이 리더로 가는 선은 결과에 증명 단계 코드(`ATTESTATION_CONDITION_*`)가 있을 때만(단일 리더 모델에는 없다), 리더 표시는 outcome대로(포함 강제는 ✓, 강제 없음은 점선 ?). 제안자가 8명을 넘으면 비율을 지켜 8명만 그리고 그렇게 썼다고 적는다. 그다음 결과 문장과 설명 줄이 나온다. 자리표시 결과(Mock)에는 그림을 그리지 않는다.
  - 두 모델은 읽을 수 있는 이름으로 보여준다("Constellation (draft rules)", "Single leader (today)"). 이름표는 문구 사전에 있고, 모르는 버전은 버전 문자열 그대로 보여준다.
  - 직접 입력과 증명 비율 sweep은 접어 둔 "Custom scenario" 안에 둔다. sweep은 0~100%를 5% 간격으로 보내고 받은 outcome을 띠로 그린다. **임계값 선은 그리지 않는다.**
  - 단계 띠(경로 → pslice → 증명 → 리더 제외)는 2026-11-11에 뺐다. 결과 문장과 설명 줄로 충분하고 글만 늘렸다.
  - Mock 모드에서는 Mock이 mock 버전에만 고정 결과를 주므로 시나리오 버튼과 직접 입력을 숨기고, 자리표시 결과 하나와 "실제 Backend에 연결해야 볼 수 있음"만 보여준다.
  - pslice, attestation, 리더 제외의 쉬운 정의는 `baypeline/be`의 Simulator README와 코드를 근거로 쓴 초안이며, Simulator 담당(최석훈)에게 확인받는 것을 권한다.
- 저장된 결과는 실패한 뒤 시도가 가리지 않는다. 마지막 시도가 404(Backend 재시작)면 저장된 결과 위에 "다시 실행" 배너를 띄운다. 배너는 저장된 기록에서 계산하므로 닫았다 열어도 남는다.

## 7. 설명 시스템 (가장 중요한 작업)

- 제목은 짧게 쓴다. 2026-11-11 수정: 블록마다 붙이던 부제 질문은 뺐다(글만 늘리고 눈이 갈 곳을 흐렸다). 답 문장이 필요한 곳(차트)에만 남긴다.
- **코드명을 화면에 내세우지 않는다**(Henry 결정). 계약 코드값(SANCTION_EXACT_MATCH, POLICY_NOT_ENFORCED, TRANSACTION_LIMIT_REACHED 등)은 자연어 문장으로 바꾸고, 그 뒤에 무슨 뜻인지 짧은 설명을 붙인다. 예: "받는 지갑이 제재 목록의 주소와 정확히 일치합니다. 정책상 이 경우 송금을 차단합니다." 코드 원문은 감사 정보와 `?` 툴팁 안에서만 보인다(추적용).
- 문장은 **계약 코드값을 문구 사전으로 옮겨 만든다**. 판단 로직이 아니다. 대상: 판정(Action), 정책 reason code, KYT ruleId, evidence type, coverage reason, 작업 상태, 오류 코드, Gateway outcome·reason, Constellation outcome·explanation.
- 정책이 왜 그 판정인지 설명할 때는 `contracts/config/policies/*.json`과 `rulesets/*.json`의 값을 읽어 인용할 수 있다(예: "이 정책은 제재 주소와 직접 거래하면 검토로 보냅니다"). 값은 읽기만 한다.
- **용어 툴팁**(Henry 결정): 솔라나 내부 용어와 전문 용어(KYT, 제재 노출, 직접 거래, fan-out, 반복 송금, 부분 분석, 토큰 계정과 소유자, 명령어 위치, 슬롯, pslice, attestation, 리더, 제안자 등)는 화면에 그대로 쓰고 **용어 자체에 점선 밑줄**을 둔다(2026-11-11 수정: `?` 아이콘은 뺐다). 마우스를 올리거나 포커스하면 한두 문장 정의가 나온다. 설명이 꼭 필요한 곳에만 쓴다. 키보드 포커스와 화면 읽기 프로그램에서도 정의를 읽을 수 있어야 한다.
- 문구 톤: 컴플라이언스 담당자의 말. 결론 먼저, 한 문단에 한 생각.
- 문구는 모두 번역 사전(영어 기본)에 둔다.

## 9. 데이터와 저장

- **저장은 브라우저 안에서**(제 판단, 2026-11-11). 발표용 데모이고 케이스 범위·로그인 대상이 상관없으므로, 외부 인증·DB 서비스(Supabase 등)를 붙이지 않는다. 로그인은 화면 흐름만 있는 데모 로그인이고, 케이스는 브라우저 저장소(IndexedDB)에 둔다. 발표장에서 외부 서비스가 하나 줄고, 계정·키를 만들 필요가 없다. 저장 계층은 인터페이스 뒤에 두어 나중에 실제 서비스로 바꿀 수 있게 한다.
- 케이스 하나에 요청 입력과 받은 응답 전체(분석 결과 두 개, 정책 심사 응답, 실행한 시뮬레이션 결과)를 **스냅샷**으로 넣는다. Backend가 재시작돼 ID가 사라져도 케이스는 읽힌다.
- 발표 전에 케이스를 미리 만들어 둘 수 있도록 케이스 내보내기·가져오기(JSON 파일)를 둔다(제 판단).
- 저장된 스냅샷도 읽을 때 계약 스키마로 검증한다.
- **케이스 = 실행(run)의 목록.** 처음 "Run case"가 첫 실행이고, 다시 실행하면 같은 케이스에 새 실행이 시각과 함께 쌓인다. 케이스 화면은 가장 최근 실행을 보여주고 이전 실행으로 바꿔 볼 수 있다. LIVE는 다시 실행하면 판정이 달라질 수 있으므로 덮어쓰지 않는다.
- **다시 연 케이스의 시뮬레이션**: 저장된 시뮬레이션 결과는 그대로 읽기 전용으로 보여준다. 새로 시뮬레이션을 돌릴 때 Backend가 그 intentId·decisionId를 더 이상 모르면(404), "Backend가 재시작되어 이 실행의 기록이 없습니다. 다시 실행하면 새 실행으로 추가됩니다"와 "Re-run case" 버튼을 보여준다. 몰래 다시 실행하지 않는다.
- Mock Backend는 상태를 브라우저 저장소에 보관해 새로고침해도 기록이 남게 한다.
- Backend 연결 모드는 세 가지다: Mock(브라우저 MSW, 오프라인) / 로컬 Backend(dev proxy) / 배포 Backend(빌드 때 주소를 넣음). 화면 상단에 지금 어느 모드인지 항상 보인다.
- **발표 안전장치**(제 판단): 배포본에서도 설정 메뉴에서 Mock으로 바꿀 수 있게 한다. 발표 중 Backend가 죽으면 Mock으로 넘어가 시연을 이어간다. Mock일 때는 "합성 데이터"가 화면에 계속 표시된다.
